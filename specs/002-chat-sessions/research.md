# Research: Chat Sessions & Persistence

**Feature**: F3 — Chat Sessions & Persistence
**Date**: 2026-06-01

---

## Decision 1: SQL Server Pagination Strategy

**Decision**: Use OFFSET / FETCH NEXT (SQL Server 2012+) via SQLAlchemy `.offset()` + `.limit()`. Keyset (cursor) pagination deferred to v2.

**Rationale**: The existing stack already uses SQL Server (mssql+aioodbc). OFFSET/FETCH is supported on SQL Server 2012+ and maps cleanly to SQLAlchemy's ORM-level `.offset()` / `.limit()`, keeping the code consistent with the rest of the backend. Keyset pagination adds complexity without a clear need at the current scale (~200 users).

**Alternatives considered**:
- Cursor/keyset pagination (next_cursor token): Better for large datasets but higher implementation complexity for v1.
- Row-number window functions: More complex SQL, unnecessary when ORM pagination suffices.

---

## Decision 2: UUID Generation

**Decision**: Generate UUIDs in Python (`uuid.uuid4()`) before insert, stored as `String(36)`.

**Rationale**: Consistent with the existing User and RefreshToken models which already use `String(36)` UUID primary keys generated by Python. Avoids SQL Server NEWID() vs NEWSEQUENTIALID() debate and keeps UUID generation testable at the service layer.

**Alternatives considered**:
- NEWSEQUENTIALID() at DB level: Better index fragmentation, but requires a server default and removes Python-level predictability for tests.

---

## Decision 3: updated_at Refresh Strategy

**Decision**: Application-level update: the session service explicitly sets `session.updated_at = datetime.now(timezone.utc)` whenever a message is added.

**Rationale**: SQLAlchemy's `onupdate` triggers on column definition work for direct ORM updates. Since message insertion requires an explicit session update anyway (to record activity), combining both in one service call is clean. Avoids a SQL Server trigger which would be an invisible side effect.

**Alternatives considered**:
- SQL Server AFTER INSERT trigger on chat_messages: Invisible, harder to test, and adds a dependency on DB-level logic.
- SQLAlchemy `onupdate=func.now()`: Works for column updates but not triggered by related table inserts.

---

## Decision 4: Audit Log Implementation

**Decision**: Create a dedicated `audit_logs` table (id, user_id, action, entity_type, entity_id, created_at, detail). Reused across the platform.

**Rationale**: The constitution requires audit logging for multiple features (session create/delete, ERP operations, tool calls). A shared `audit_logs` table avoids per-feature logging schemas and provides a single place to query for compliance reviews.

**Alternatives considered**:
- Structured logging to file/stdout only: Not queryable; insufficient for compliance.
- Per-feature log tables: Duplication; inconsistent schema.

---

## Decision 5: Bot Foreign Key Constraint

**Decision**: Store `bot_id` as `String(36)` in `chat_sessions` without a hard FK constraint at the DB level for v1, since the `bots` table is created in F2 (not yet implemented). Add a migration to add the FK constraint once F2 is done.

**Rationale**: Avoids blocking F3 implementation on F2. The application layer validates bot access (user is authorized for the bot) before creating a session, maintaining integrity at the service level.

**Alternatives considered**:
- Create a stub `bots` table in this migration: Creates premature schema; conflicts with F2's full implementation.

---

## Decision 6: Message Role Constraint

**Decision**: `role` column as `String(20)` with a `CHECK (role IN ('user', 'assistant'))` constraint. Mirrors the pattern used for `UserRole` in the users table.

**Rationale**: Consistent with the project's SQL Server constraint pattern (no native ENUM). FastAPI/Pydantic enforces the enum at the API layer; the DB constraint is a safety net.

---

## Decision 7: Message Content Storage

**Decision**: `NVARCHAR(MAX)` for message content (mapped as `Text` in SQLAlchemy).

**Rationale**: LLM responses can be arbitrarily long. `NVARCHAR(MAX)` stores up to ~2GB and supports Unicode, which is required for multi-language conversations. Indexed search on content is out of scope for v1.

---

## Decision 8: Session Isolation Enforcement

**Decision**: Every query touching sessions or messages MUST include both `session_id` AND `user_id` conditions. Services resolve `user_id` from the JWT dependency — it is never passed as a request body parameter.

**Rationale**: Defence-in-depth. Even if a session_id is guessed or leaked, it cannot be accessed without the matching user identity from the verified JWT.

---

## Decision 9: Concurrent Message Prevention

**Decision**: Not enforced at DB level for v1. The session service will be called once per user message submission. True concurrent collision is unlikely at v1 scale. F4 will implement a single-in-flight guard per session when it manages LLM streaming.

**Rationale**: Pessimistic locking or Redis-based mutexes add operational complexity not justified at ~200 users.
